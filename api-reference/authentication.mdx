title: "Authentication"
description: "Establish a wallet-bound session by signing a one-time challenge. No email, password, or API key."
---

The Aura API uses **wallet-bound sessions**, the same mechanism as the Aura
app (whose embedded wallet signs the challenge with its groupless secp256k1
key). There are no API keys.

- **Reads are public.** Every `GET` endpoint works without authentication
  (subject to the anonymous per-IP [rate limits](/api-reference/rate-limits)).
- **Writes require a session.** Mutating endpoints (comments, watchlist,
  notifications, profile writes) and the build-tx endpoints under `/v1/tx/*`
  require a valid session, presented either as a **cookie plus CSRF header** or
  as an **`Authorization: Bearer` token**.

The session authorises off-chain writes only. On-chain actions come back as
*unsigned* transactions that your wallet signs locally, so the API never holds
keys and the session can never move funds.

## Establishing a session

Two-step wallet-signature flow:

<Steps>
  <Step title="Get a one-time challenge">
    ```bash
    curl -X POST https://api.aurabets.io/v1/auth/challenge \
      -H 'content-type: application/json' \
      -d '{"address": "3Cef...your-wallet"}'
    ```

    Response:

    ```json
    {
      "challenge": "Sign this message...",
      "expiresAt": "2026-07-01T19:00:00Z"
    }
    ```

    `address` is optional. Omit it when the wallet address is only known
    after authentication, then pass the exact `challenge` text in the next
    step.
  </Step>
  <Step title="Sign with your wallet">
    Use your wallet's `signMessage` helper with `hasher: "alephium"` to sign
    the `challenge` string. `keyType` identifies the signature scheme:

    | `keyType` | Wallet |
    | --- | --- |
    | `gl-secp256k1` | Groupless secp256k1, which is what the Aura app's embedded wallet uses (addresses start with `3`) |
    | `default` | Grouped secp256k1, for standard Alephium wallets and tooling (addresses start with `1`) |

    These two are the only accepted values. Build-tx endpoints take the same
    `signerKeyType` field, and it must match the key your `signerAddress` was
    derived from.

    If you're not in JavaScript, see
    [the signing scheme](#the-signing-scheme-for-non-javascript-clients) for
    the exact bytes.
  </Step>
  <Step title="Exchange the signature for a session">
    ```bash
    curl -X POST https://api.aurabets.io/v1/auth/session \
      -H 'content-type: application/json' \
      -c cookies.txt \
      -d '{
        "address":   "3Cef...your-wallet",
        "publicKey": "0233...your-pubkey",
        "signature": "abcd...sig",
        "keyType":   "gl-secp256k1"
      }'
    ```

    Response:

    ```json
    {
      "address": "3Cef...your-wallet",
      "csrf": "5f2a...token",
      "created": false
    }
    ```

    The session itself is set as an **HttpOnly cookie** (30-day TTL with
    sliding refresh). Keep the `csrf` value, because every mutating request
    must echo it back in the `x-csrf-token` header.

    First sign-in also creates the account server-side with a **generated
    unique username**; manage it via `GET/PATCH /v1/users/me` and
    `GET /v1/users/username-available`.
  </Step>
</Steps>

## The signing scheme (for non-JavaScript clients)

`@alephium/web3` hides this behind `signMessage`, but the scheme is small
enough to implement directly in any language. The `alephium` hasher prefixes
the message before hashing, which is what stops a signed login from ever being
mistaken for a signed transaction:

```
digest    = blake2b-256( utf8("Alephium Signed Message: " + challenge) )
signature = secp256k1 sign over that 32-byte digest
```

Encodings on the wire, all lowercase hex without a `0x` prefix:

| Field | Format |
| --- | --- |
| `publicKey` | 33-byte compressed secp256k1 point, 66 hex chars |
| `signature` | 64-byte raw `r \|\| s`, 128 hex chars. Not DER, and no recovery byte |
| `address` | base58. Groupless keys give a 53-char address starting with `3` |

<Warning>
  The literal prefix is `Alephium Signed Message: ` with a single trailing
  space, and it is hashed as UTF-8. Getting the prefix or the digest wrong
  produces a signature that verifies against nothing, which surfaces as a
  generic `401 invalid signature`.
</Warning>

Here is the whole flow in Python, with no Aura or Alephium dependency:

```python
import hashlib, requests
from coincurve import PrivateKey  # pip install coincurve requests

API = "https://api.aurabets.io"
ADDRESS = "3cUq...your-wallet"
key = PrivateKey(bytes.fromhex("your-32-byte-private-key-hex"))

s = requests.Session()

# 1. Ask for a challenge.
challenge = s.post(f"{API}/v1/auth/challenge", json={"address": ADDRESS}).json()["challenge"]

# 2. Hash it the way Alephium does, then sign the digest.
digest = hashlib.blake2b(
    ("Alephium Signed Message: " + challenge).encode("utf-8"), digest_size=32
).digest()
signature = key.sign_recoverable(digest, hasher=None)[:64]  # drop the recovery byte

# 3. Exchange it for a session, asking for a bearer token.
session = s.post(f"{API}/v1/auth/session", json={
    "address":     ADDRESS,
    "publicKey":   key.public_key.format(compressed=True).hex(),
    "signature":   signature.hex(),
    "keyType":     "gl-secp256k1",
    "issueToken":  True,
}).json()

s.headers["Authorization"] = f"Bearer {session['token']}"

# 4. Authenticated from here on, with no cookie jar and no CSRF header.
print(s.get(f"{API}/v1/users/me").json())
```

## Bearer tokens for bots and backends

Cookies are a browser convenience and a nuisance everywhere else. Pass
`issueToken: true` to `POST /v1/auth/session` and the response body includes the
token, which you then send as a header:

```bash
curl https://api.aurabets.io/v1/users/me \
  -H "authorization: Bearer $AURA_TOKEN"
```

It is the same credential as the cookie, with the same 30-day lifetime, so
three things differ and nothing else does:

| | Cookie | Bearer |
| --- | --- | --- |
| `x-csrf-token` on writes | Required | Not required |
| Sliding refresh | Automatic | None. Re-run challenge and sign on a `401` |
| Where you keep it | Browser handles it | You store it, so treat it like a key |

Skipping CSRF for bearer callers is safe rather than a shortcut. CSRF exists
because browsers attach cookies to cross-site requests on their own, and nothing
attaches an `Authorization` header on its own. Re-authenticating is also cheap
when you hold the signing key, so on a `401` just run the challenge flow again
rather than building refresh logic.

<Warning>
  A session token is a bearer credential for your account's off-chain actions.
  It cannot move funds, since on-chain actions still need your wallet signature,
  but it can post as you. Individual tokens cannot be revoked, so keep them in a
  secret store and re-authenticate rather than persisting them somewhere loose.
</Warning>

## Making authenticated requests

Send the session cookie **and** the CSRF header on every mutating request:

<CodeGroup>
```bash curl
curl -X PATCH https://api.aurabets.io/v1/users/me \
  -b cookies.txt \
  -H "x-csrf-token: $CSRF" \
  -H 'content-type: application/json' \
  -d '{"bio": "Sports and elections."}'
```

```ts TypeScript (fetch)
const res = await fetch('https://api.aurabets.io/v1/users/me', {
  method: 'PATCH',
  credentials: 'include', // sends the HttpOnly session cookie
  headers: {
    'content-type': 'application/json',
    'x-csrf-token': csrf,
  },
  body: JSON.stringify({ bio: 'Sports and elections.' }),
})
```

```py Python (requests)
import requests

s = requests.Session()
# ...challenge + session calls populate s.cookies...
res = s.patch(
    'https://api.aurabets.io/v1/users/me',
    headers={'x-csrf-token': csrf},
    json={'bio': 'Sports and elections.'},
)
```
</CodeGroup>

`GET` requests never need the CSRF header. They need only the cookie, and only
on endpoints that return caller-specific data. Bearer callers never need it at
all.

## Session lifecycle

| Endpoint | Purpose |
| --- | --- |
| `POST /v1/auth/challenge` | Mint a one-time nonce to sign (5-minute expiry). |
| `POST /v1/auth/session` | Verify the signature, create/refresh the account, set the session cookie. Sign-in **and** registration. |
| `GET /v1/auth/session` | Check whether the cookie is still valid and recover the CSRF token. |
| `POST /v1/auth/logout` | Clear the session + CSRF cookies. |

<Warning>
  Build-tx endpoints under `/v1/tx/*` additionally enforce that the
  transaction's **signer equals the session wallet**, so a session for wallet A
  can never build a transaction that spends from wallet B.
</Warning>
