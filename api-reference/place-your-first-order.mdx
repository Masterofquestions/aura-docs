Aura trading is instant off-chain matching with batched Clearinghouse
settlement. Orders are **not** individual on-chain CLOB transactions. Do not use
the deleted `/v1/tx/markets/{address}/orders`, `market-orders`, or per-order
build/sign/submit flow.

The secure API path keeps builder identity and user authority separate:

<Steps>
  <Step title="Read the active protocol configuration">
    ```ts
    const config = await aura.protocol.config()
    if (config.network.name !== expectedNetwork) throw new Error('wrong Aura network')
    ```

    Use its collateral decimals, lot size, fee rate, lifetime and batch limits.
    Do not copy these values from a tutorial.
  </Step>
  <Step title="Create a narrowly scoped developer key">
    The builder owner creates a key with only the needed scopes, for example
    `market:read`, `realtime:public`, `account:read`, `trade:place` and
    `trade:cancel`. The key controls identity and quota, not assets.
    Save the returned `key.builderCode` as the builder's canonical public
    attribution identity. It is not a secret.
  </Step>
  <Step title="Establish a wallet session for private reads">
    The user signs a one-time Aura login challenge. Use the resulting session
    for spendable-aware quotes, account snapshots and private realtime topics.
    The order write itself uses the developer key plus the restricted trading
    authorization, not this session bearer.
  </Step>
  <Step title="Have the user create restricted trading authority">
    The authorization is held by Aura's enclave and limited by expiry and
    trading caps. The user can inspect, rotate and revoke it. Neither seed
    material nor intent/cancel signatures are exposed to the builder. Creation
    happens only in Aura's signer iframe/first-party authorization console; its
    one-time `aura_trade_…` secret is delivered to the chosen builder for
    server-side storage. The user binds the authorization to the exact
    `builderCode` returned with the developer key; Aura rejects order writes
    when those identities do not match.
  </Step>
  <Step title="Preview BUY or SELL with the canonical matcher">
    ```ts
    const quote = await aura.markets.quote(marketAddress, {
      outcome: 'yes',
      side: 'buy',
      orderType: 'gtc_limit',
      quantityBaseUnits: baseUnits('1000000000000000000'),
      limitPriceTick: priceTick(625),
      expectedBookVersion: snapshot.bookVersion,
    })
    ```

    Check `expiresAt`, warnings, required collateral, unfilled quantity and the
    current book version. A quote is never a guaranteed fill.
  </Step>
  <Step title="Submit idempotently and observe lifecycle events">
    Semantic order submission is `POST /v1/orders` with a developer key in
    `x-aura-developer-key` and the user's authorization in
    `x-aura-trading-authorization`. Aura derives the authorization owner,
    registered-market witness, network, nonce, timestamps and intent, injects
    the authenticated key's canonical `builderCode`, then signs and submits
    internally. Do not add a caller-selected `builderCode` to the order body;
    it is not accepted. The
    response contains an intent hash and may contain a public sequencer-signed
    acknowledgement for client verification. It never contains the intent's
    custody signature, a cancellation authorization or a reusable signing
    grant.

    ```ts
    const placed = await aura.orders.place({
      clientOrderId: baseUnits('42'),
      marketId: quote.marketId,
      outcome: 'yes',
      side: 'buy',
      orderType: 'gtc_limit',
      quantityBaseUnits: baseUnits('1000000000000000000'),
      limitPriceTick: priceTick(625),
      expectedBookVersion: quote.bookVersion,
      expiresAt: new Date(Date.now() + 60_000).toISOString(),
    })
    ```

    Supply exactly one of `quantityBaseUnits` or BUY-only `spendBaseUnits`.
    IOC SELL requires `costBoundBaseUnits` as minimum proceeds. The API rejects
    stale, expired or authorization-policy-violating requests.

    Persist the exact body. After an ambiguous transport failure, retry the
    same `clientOrderId`, `expiresAt` and terms; recomputing expiry creates a new
    logical request.

    An accepted order is initially provisional. Subscribe to the user's order,
    funding, settlement and account topics after the account snapshot cursor.
    Treat settlement confirmation as final for analytics; an earlier match can
    still unwind or fail funding.
  </Step>
</Steps>

## Order state is not one boolean

Builders should preserve the states emitted by Aura, including accepted, open,
partially filled, matched/provisional, cancel pending, cancelled, settled,
unwound and funding failed. Do not remove an order from the UI before its
replacement position, settlement or correction state is available.

## Cancellation and dead-man switch

Batch cancellation is non-atomic and returns a result for each target. A fill
may win the race for one order while another cancellation succeeds. Reusing the
same idempotency key must return the original result rather than executing a
second batch.

Market makers can arm a durable dead-man switch. Refresh it only while the
authenticated control surface is alive. If the heartbeat expires, Aura creates
exact one-use cancellations through the normal escrow/tombstone path. Aura does
not keep a reusable pre-signed cancel-all transaction.

<Warning>
  In a browser, a dead-man switch heartbeat is tab-only. Tell the user clearly
  that closing the tab, sleeping the device or losing connectivity will trigger
  cancellation. Never arm it silently.
</Warning>

The public management operations are:

| Operation | Route |
| --- | --- |
| Place semantic BUY/SELL request | `POST /v1/orders` |
| Advanced pre-encoded intent compatibility | `POST /v1/orders/raw` |
| Submit one canonical unsigned cancel command | `POST /v1/orders/cancel` |
| Cancel explicit hashes, all, or an owner-scoped filter | `POST /v1/orders/cancel-batch` |
| Read a batch by idempotency key | `POST /v1/orders/cancel-batch/status` |
| Arm/refresh/disarm/status | `POST /v1/orders/dead-man-switch/{operation}` |

Filtered cancellation returns at most 100 newest orders. If `selection.truncated`
is true, continue with `nextBeforeSequence` and a **new** idempotency key. A
retry of the same page keeps the original key.

## Advanced raw compatibility gate

New builders should use semantic `orders.place()`. `intentHex` exists only on
advanced `orders.placeRaw()`, while single-order `commandHex` remains an
unsigned fixed-format cancellation command. Use Aura's audited canonical
format package for either raw message; never reverse-engineer the binary layout
from an example, call wallet-svc/enclave internal routes, or request a custody
signature from the API.
